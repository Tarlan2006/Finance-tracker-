# ЗАДАНИЕ ДЛЯ CODEX: несколько пользователей (аккаунты, раздельные таблицы)

Приложение работает и опубликовано (https://finance-tracker.tarlan-b06.workers.dev). Сейчас оно одиночное: один общий ключ `APP_KEY` и одна таблица `SHEET_ID`. Нужно сделать **аккаунты**: каждый человек входит под своим логином и паролем, устройство запоминает вход, у каждого аккаунта **своя Google-таблица**, данные не пересекаются.

Первые два аккаунта:

| login | Отображаемое имя | Таблица |
|---|---|---|
| `tarlan` | Tarlan | существующая (`SHEET_ID` из секретов), данные не трогать |
| `aru` | Aru | новая, пустая; создаётся позже, администратор привяжет её скриптом |

Вопросов не будет: решай сам, записывай решения в `DECISIONS.md`, итог в `MULTIUSER_REPORT.md`. Перечитай `CODEX_PROMPT.md`, `AGENTS.md`, `DESIGN_REPORT.md`, `MOTION_REPORT.md`, `FIXES_REPORT.md`, `LOGO_REPORT.md`.

## 0. Жёсткие правила (остаются в силе)

- Боевая таблица Tarlan **неприкосновенна**: правила записи прежние (первая пустая строка по A:D, только A:E и G:H, колонка F не трогается, без append/insert/delete строк, ограничение 1006 строк, правка и удаление через отпечаток и очистку значений). Адаптер для существующей таблицы не менять по поведению.
- Живую запись в боевые таблицы **не выполнять**. Браузерные тесты только на mock. `SMOKE_WRITE` не запускать. Никаких обращений к боевому Google Sheets Aru (её таблицы ещё нет).
- **Не запускай административные скрипты против боевого Worker**: создание аккаунта `aru`, сброс паролей и привязку таблицы выполнит человек сам по твоей инструкции.
- `git push` не делать. Секреты, пароли и хеши в git, логи, отчёты и снимки не попадают. **Не записывай никакие реальные пароли в репозиторий** (ни в тесты, кроме явно фиктивных, ни в документацию, ни в `.env`-примеры).
- Использовать `npm.cmd` / `npx.cmd`. Без новых тяжёлых зависимостей; суммарный JS не больше ~110 КБ gzip, CSS не больше ~10 КБ gzip.
- Все интерфейсные тексты на русском. Дизайн, токены, анимации и доступность сохраняются.

## 1. Модель аккаунтов

1. Хранилище аккаунтов: отдельный Durable Object (`AccountsDO`, один экземпляр) на SQLite-хранилище, а не секреты Worker (приложение должно уметь менять пароль само). Для каждого аккаунта: `login` (строчные латинские буквы/цифры, 2–32 символа, уникален без учёта регистра), `displayName`, хеш пароля (PBKDF2-SHA-256 через WebCrypto, случайная соль 16+ байт, число итераций подбери **измерением** под лимит CPU вашего тарифа Workers; запиши измерения в отчёт и выбери максимум, при котором вход стабильно укладывается в лимит; если надёжно получается менее 100 000, объясни риск и компенсируй блокировками), флаг `mustChangePassword`, `sheetId` (может быть пустым), `createdAt`, `passwordChangedAt`.
2. **Сессии:** после успешного входа устройство получает случайный непрозрачный токен (не менее 32 байт случайности, в базе хранится только его хеш). Срок жизни скользящий, около 180 дней. Токен хранится на устройстве там же, где раньше хранился ключ, и отправляется в заголовке как раньше (выбери имя заголовка/схему сам). Сессия привязана к аккаунту; список сессий с примерной меткой устройства (User-Agent, дата последнего использования) доступен в «Ещё → Аккаунт». Выход отзывает сессию на сервере. Смена пароля отзывает все остальные сессии этого аккаунта. Любая сессия может быть отозвана администратором.
3. **Все маршруты `/api/*` определяют аккаунт только по сессии.** Идентификатор таблицы **никогда не принимается из запроса**: сервер берёт `sheetId` из записи аккаунта. Аккаунт без привязанной таблицы получает понятный ответ «таблица ещё не подключена» (интерфейс показывает экран ожидания с инструкцией: обратитесь к администратору).
4. Раздельная сериализация записей: Durable Object записи (как сейчас) адресуется по **аккаунту/таблице**, чтобы записи разных аккаунтов не блокировали друг друга, а записи одного аккаунта шли строго последовательно. Все кеши, ревизии настроек (`rev`), служебные листы и ответы сводок привязаны к таблице аккаунта и не смешиваются.
5. **Миграция без потери доступа.** Если в `AccountsDO` ещё нет ни одного аккаунта, а секрет `APP_KEY` существует, при первом обращении Worker создаёт аккаунт `tarlan` (displayName «Tarlan», `sheetId` = текущий `SHEET_ID`) с паролем, равным текущему значению `APP_KEY` (человек его знает), `mustChangePassword=false`. Это выполняется один раз и атомарно, повторный запуск ничего не дублирует. После этого `APP_KEY` больше не принимается для входа в приложение. Тот же механизм не создаёт `aru`.
6. `GET /api/accounts` без авторизации возвращает только `[{login, displayName}]` для выпадающего списка входа (больше ничего: ни таблиц, ни дат). Ограничь частоту запросов. Отметь в `DECISIONS.md`, что список логинов виден любому, кто знает адрес приложения; это осознанное решение владельца.

## 2. Безопасность входа

- `POST /api/login {login, password}`: сравнение хеша за постоянное время; одинаковый ответ и время для «нет такого аккаунта» и «неверный пароль» (при отсутствии аккаунта всё равно считай фиктивный хеш).
- Ограничение попыток: по паре (IP из `CF-Connecting-IP`, login) и по login отдельно. После 5 неудач подряд блокировка на 15 минут с нарастанием (до 24 часов при продолжении); успешный вход сбрасывает счётчик. Ответ при блокировке: 429 с понятным текстом и `Retry-After`. Блокировка конкретного аккаунта не должна давать злоумышленнику способ навсегда заблокировать владельца: вход с уже доверенной сессией продолжает работать.
- Пароль: минимум 5 символов (владелец осознанно может задать простой пароль; в интерфейсе смены пароля показывай оценку надёжности и совет, но не запрещай). Максимум 128. Пароли и токены не логируются, не попадают в URL, в ответы ошибок и в сообщения телеметрии.
- `mustChangePassword`: после входа такой аккаунт может вызвать **только** смену пароля и выход; интерфейс сразу показывает экран «Задайте свой пароль» (новый пароль дважды). Пока пароль не сменён, остальные маршруты отвечают 403 с кодом `must_change_password`.
- Смена пароля (`Ещё → Аккаунт → Сменить пароль`): требует текущий пароль, отзывает остальные сессии, обновляет `passwordChangedAt`.
- Заголовки безопасности, `no-store` для `/api/*`, CSP и запрет кеширования API в service worker остаются.

## 3. Административные средства

Административные маршруты `/api/admin/*` включены только при заданном секрете `ADMIN_TOKEN` (иначе 404), сравнение за постоянное время, отдельное ограничение частоты, выключены для сессий пользователей. Скрипт `scripts/accounts.mjs` (Node, без новых зависимостей) читает `WORKER_URL` и `ADMIN_TOKEN` из `.dev.vars` или окружения и поддерживает команды:

- `list` — логины, имена, наличие таблицы, `mustChangePassword`, число активных сессий, дата последней смены пароля. Без хешей.
- `add <login> <displayName> [--must-change]` — создаёт аккаунт; пароль запрашивается **интерактивно со скрытым вводом и повторным вводом**, никогда не принимается аргументом командной строки и не печатается.
- `set-password <login> [--must-change]` — сброс пароля, отзыв всех сессий.
- `set-sheet <login> <ссылка-или-id-таблицы>` — разбирает ссылку Google Sheets, проверяет формат ID, **запрещает привязку той же таблицы к двум аккаунтам**, сохраняет. Печатает email сервисного аккаунта, которому нужно дать доступ «Редактор» (бери из конфигурации Worker; не печатай приватный ключ и ничего лишнего).
- `revoke <login>` — отзыв всех сессий.
- `disable`/`enable <login>` — отключение входа без удаления данных.

Добавь `scripts/accounts.mjs` в README с примерами и **пошаговой инструкцией для человека** для запуска на боевом Worker. Предусмотри в `.dev.vars.example` (если файла нет, создай) имена переменных без значений. Генерацию `ADMIN_TOKEN` опиши командой (случайные 32 байта) и загрузку через `wrangler secret put ADMIN_TOKEN`. Не создавай и не отправляй секреты сам.

## 4. Вход и интерфейс

1. Экран входа: **выпадающий список аккаунтов** (нативный `<select>`, значения приходят из `GET /api/accounts`) и поле пароля; кнопка «Войти». Последний выбранный логин запоминается на устройстве. Ошибки: неверный пароль, блокировка (с временем), нет сети. Автозаполнение паролей браузера должно работать (корректные `autocomplete`/`name`), фокус и клавиатура на телефоне работают штатно. Логотип на экране входа остаётся.
2. «Ещё → Аккаунт»: имя и логин, «Сменить пароль», «Устройства и сессии» (список, отзыв отдельной сессии), «Выйти». Шапка «Ещё» не должна ломаться.
3. После входа приложение открывается на «Траты» выбранного аккаунта. Данные, кеш и настройки другого аккаунта не должны мелькать при переключении (кеш IndexedDB и локальные настройки привязаны к `accountId`; при выходе и смене аккаунта они не читаются).
4. **Очередь офлайн-записей и её шифрование привязаны к аккаунту.** Выход шифрует очередь этого аккаунта, вход другого аккаунта на том же устройстве её не видит и не отправляет. **Миграция:** существующая неотправленная очередь без привязки (из версии до аккаунтов) должна быть автоматически закреплена за аккаунтом `tarlan` и **не потеряна** при первом входе после обновления; только `tarlan` может её увидеть. Покрой тестами, включая сценарий «очередь с записями, обновление, вход tarlan, записи отправлены ровно один раз».
5. Идемпотентные ID записей и защита от дублей работают как прежде, в пределах таблицы аккаунта.
6. Глубокие ссылки автоввода (`/?amount=…&merchant=…&src=…`) работают после входа: если сессии нет, параметры сохраняются на время входа в `sessionStorage` и подставляются после успешного входа, затем очищаются из адресной строки.

## 5. Новая пустая таблица («первая настройка»)

Для аккаунта, у которого таблица подключена, но **не инициализирована** (нет листа с расходами), экран «Траты» вместо ошибки показывает «Таблица подключена, но пуста» и кнопку **«Подготовить таблицу»**. Правила:

1. Подготовка допускается **только** если в таблице нет листа «Ввод данных» и нет листов `FT Categories` / `FT Items`. Если лист расходов уже существует, кнопка не должна ничего создавать или менять; покажи понятное объяснение. Проверка выполняется на сервере при каждом вызове, не доверяй клиенту.
2. Структурные операции (создание листов, переименование пустого листа по умолчанию, заголовки, формат, формула колонки F) разрешены **исключительно** в этом режиме и только для неинициализированной таблицы аккаунта. Для инициализированных таблиц белый список операций адаптера остаётся прежним (запрещены append/insert/delete и т. п.). Опиши и протестируй явное разделение «режим подготовки» / «обычный режим».
3. Создаваемая структура: лист «Ввод данных» ровно с тем же контрактом, что у таблицы Tarlan (A дата, B название, C категория, D сумма, E по контракту, F формула месяца как в прежней таблице, G ID, H источник; заголовки в первой строке; сетка 1006 строк; формат даты и суммы такой же). **Образец контракта возьми из кода и тестов проекта и из `CODEX_PROMPT.md`**, а формулу F2 и заголовки узнай только чтением из mock/описания контракта; в боевую таблицу Tarlan за образцом не ходи. Листы `FT Categories` и `FT Items` с теми же заголовками и логикой, что уже создаются в режиме «Создать» настроек.
4. Начальные категории — короткий нейтральный набор (например: Продукты, Кафе и рестораны, Транспорт, Здоровье, Покупки и одежда, Развлечения, Подарки, Прочее) с эмодзи и лимитами 0 (без лимита); пользователь меняет их в настройках как обычно. Доходы и ежемесячные расходы создаются пустыми; пока их нет, бюджет показывает «Укажите доходы в настройках» без деления на ноль. Не копируй категории и суммы Tarlan.
5. Операция идемпотентна и восстанавливается после частичного сбоя (повторный вызов дописывает недостающее и не дублирует листы).
6. После подготовки аккаунт работает как обычный; режим совместимости со старыми листами «Справочник»/«Доходы и расходы»/«Дашборд» для новых таблиц **не используется**.

## 6. Тесты

Все прежние тесты остаются зелёными. Добавь и запусти:

- unit/API: хеширование и сравнение пароля, блокировки и нарастание, одинаковые ответы при отсутствии аккаунта, формат/срок сессий, отзыв при смене пароля, `mustChangePassword` блокирует остальные маршруты, миграция `tarlan` из `APP_KEY` (один раз, атомарно, без повторного создания), административные маршруты выключены без `ADMIN_TOKEN` и закрыты для пользовательских сессий, запрет привязки одной таблицы к двум аккаунтам.
- **Изоляция:** сессия `aru` не может читать, писать, экспортировать, менять настройки или видеть сводки таблицы `tarlan` ни одним маршрутом, ни подменой параметров, заголовков или тела; mock-адаптер должен поддерживать несколько таблиц, тест проверяет, что запись аккаунта A не изменяет таблицу B и что очереди обработки не блокируют друг друга.
- Пустая таблица: режим подготовки создаёт структуру в mock, повтор не дублирует, частичный сбой восстанавливается, отказывает на таблице с существующим листом «Ввод данных», не вызывается из обычного режима, записи после подготовки соблюдают прежний контракт (A:E, G:H, F не трогается).
- Браузерные (Playwright, mock, обе темы): вход через выпадающий список, запоминание выбора, неверный пароль, блокировка, принудительная смена пароля, смена пароля, выход, повторное открытие без ввода пароля, вход другого аккаунта на том же устройстве без утечки данных и очередей, миграция существующей очереди на `tarlan`, экран «Подготовить таблицу», глубокая ссылка через вход, сессии и отзыв.
- Сканер секретов и проверка, что в репозитории, логах, снимках и отчёте нет паролей, токенов и хешей. Размеры сборки в пределах.
- Скриншоты экранов входа, «Аккаунт», смены пароля, «Подготовить таблицу» (mock) для 360, 412, 768 и 1440 px в обеих темах в `tests/screenshots/multiuser/`; просмотри их сам.

## 7. Публикация

После зелёных `lint`, `tsc`, `vitest`, `playwright`: `npm.cmd run build`, `npm.cmd run deploy`, затем `node scripts/verify-deployment.mjs` **только чтением**. Скрипт проверки раньше использовал `APP_KEY`: переведи его на вход аккаунтом через переменные `VERIFY_LOGIN`/`VERIFY_PASSWORD` из `.dev.vars` (если их нет, скрипт проверяет только публичные части: health, 401 без сессии, заголовки, список `/api/accounts`, и честно сообщает, что чтение данных пропущено). Не выполняй административные команды против боевого Worker и не создавай аккаунты в боевой среде. Коммиты по логическим группам (хранилище аккаунтов и сессии; безопасность входа; админ-скрипт; интерфейс входа и аккаунта; изоляция очереди и кеша; подготовка пустой таблицы; тесты и документация). `git push` не выполнять.

**Порядок после деплоя** (его выполняет человек; опиши в README и в `MULTIUSER_REPORT.md` точными командами для PowerShell):
1. Первый вход `tarlan` со старым паролем (значение прежнего `APP_KEY`) — проверить, что данные на месте и офлайн-очередь не потеряна.
2. Создать `ADMIN_TOKEN` и загрузить как секрет, затем `node scripts/accounts.mjs add aru Aru --must-change` (пароль вводится в скрытом запросе).
3. Aru создаёт пустую таблицу и даёт доступ «Редактор» сервисному аккаунту; затем `node scripts/accounts.mjs set-sheet aru <ссылка>`.
4. Aru входит, меняет пароль на свой, нажимает «Подготовить таблицу».
